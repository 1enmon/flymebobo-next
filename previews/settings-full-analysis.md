### A2. 入口卡子页面

**应用规则**（AppRulesActivity）：给每个应用单独设气泡行为，三档单选「跟随全局 / 永不弹 / 只贴边」，搜索框，即时生效。说明文：「永不弹：通知不进气泡（通知栏照常）· 只贴边：只进左侧贴边扇子，不弹胶囊 · 跟随全局：按总开关走」。与场景例外是两道串联的门：场景例外决定场景内放行还是排队，应用规则决定待遇（设了永不弹，放行了也被拦）。

**场景例外**（SceneExceptionsActivity）：横屏游戏/视频全屏时通知先排队、退出场景补弹；名单内应用「突破弹出」。两档「跟随拦截 / 突破弹出」，默认突破：微信、QQ。来电永远照常。游戏名单三路识别（系统分类+引擎特征+内置名单+线上 games.txt，6 小时拉一次）。

**临时静默**（TempSilenceActivity）：状态卡（开启/倒计时/提前取消）+「静默时长」三档 chips（30 分钟 / 1 小时默认 / 2 小时）+「联动与突破」两开关：与系统勿扰联动（默认开）、静默时来电突破（默认开）+ 无勿扰授权时的红色提示框和「去授权」按钮。静默时普通通知排队、恢复补弹；音乐/下载/实况不入队。

## 二、重叠与冲突分析

### 2.1 同一件事被多个开关管（真重叠）

1. **「点空白处消散」出现在三处**：通知气泡卡的说明里写了一遍行为、自动消散是独立开关、大卡片模式说明里又写了一遍（大卡片点空白消散成图标）。用户想关这个行为要在两张卡之间猜。
2. **展开卡片 × 大卡片模式 × 小窗打开 = 一条链上的三段**：通知呈现（胶囊 or 直接大卡）→ 点胶囊（展开 or 不展开）→ 点卡片（小窗 or 全屏）。现在拆成三张平级卡，其中 bigCard 打开后，card 开关对普通通知基本失效（已经是卡片了，没胶囊可点）——这是**模式关系伪装成三个开关**，且互相的优先级没有任何一处说明。
3. **音乐卡片 vs 展开卡片**：同一个「点胶囊展开」概念被拆成两个开关（card 管普通、musicCard 管音乐），用户必须读说明才知道展开卡片「不含音乐」。
4. **「不弹」的三套机制、三套词**：应用规则「永不弹/只贴边」、场景「排队/突破」、临时静默「排队/补弹」——底层都是"抑制弹出+事后处理"，但三页各用一套术语，用户要建立三次心智模型。且三者叠加时的优先级（静默中 + 场景内 + 永不弹）只在代码里成立，界面无任何一处交代。

### 2.2 同概念不同档位（本该单选）

5. **呈现模式**：先胶囊 / 直接大卡片 = 二选一模式，现为 bigCard 一个布尔开关挂在平级，和它改造的对象（通知气泡、展开卡片）平起平坐。
6. **扇子透明度**：历史上先有手动透明度滑条（v459 已撤），现为 fanAutoDim 开关在顶层、扇子其余外观（位置/重叠/方向）却在外观卡内——同一个对象的设置被劈成两处。

### 2.3 粒度不一致（同类项不同层级）

7. **外观类开关散落**：胶囊自动取色、胶囊滚动、扇子自动变淡是顶层卡（各占一行），而胶囊圆角/高度/宽度等细项却埋在外观卡里。取色和滚动与「胶囊宽度」是同一类东西（胶囊长什么样），层级却差一级。
8. **打码四开关全嵌在验证取件码卡里**：打码已经是一个完整功能（总开关+场景分开关+范围开关），借住在「验证取件码」卡内，卡名与内容对不上——找打码的人要先想到取件码。
9. **来电高度滑条被 callRight 门控**：代码注释（v442）写明来电高度滑条只有「来电放右边」开着才能滑、关着置灰——但高度对左侧来电同样有意义，这是实现耦合漏进了信息架构。

### 2.4 低频/一次性/工具类占行

10. **模拟来电、模拟音乐**：纯调试工具（调位置/大小时看效果），常驻在来电卡、音乐卡的展开区里，普通用户永远用不到，还各带一段长说明。
11. **QQ音乐flyme版免费听**：v345 起开关已删除、功能常开，设置页只剩一条无开关的展示行嵌在音乐卡里——占位但不可操作。
12. **反方向的钟**：娱乐彩蛋（音乐跑马灯），还带 100 次点击解锁门槛，嵌在音乐卡里；它和音乐卡片、模拟音乐、6 条滑条挤在同一个展开区，音乐卡是全页展开后最长的卡。

### 2.5 死功能核查（要有证据才写）

- **没有发现已失效的开关**：逐个核对 FeatureFlags 23 个标志位的读取点——notif/music/dl/code/live/card/miniwindow/blankDissipate/autoDestroy/musicCard/bigCard/callRight/fanAutoDim/musicLed 均在 BubbleWindow 被读，scroll/autoTint/mask/maskApps 在 CapsuleView/PrivacyMask 被读，maskLock/maskRecord 在 PrivacyMask 被读。
- simCall/simMusic 不读标志位字段、只响应 FEATURE_TOGGLE 广播事件弹/收假胶囊（FeatureFlags 类注释明示「只响应开关翻动」），是事件型工具，不是死开关。
- qqFree 标志位恒 true、开关已删，但功能本体活着（XposedEntry 仍 install QQFreeMode）——是「无开关的常开功能」，不是死功能。
- 唯一被撤过的设置项是扇子手动透明度滑条（v459 撤除，代码注释留痕），现已不在界面上，不算死功能。

### 3.2 每个合并动作 + 理由

| # | 动作 | 理由 |
|---|---|---|
| 1 | 展开卡片 + 大卡片模式 + 小窗打开 → 合并为「打开方式」卡：卡内含「呈现」单选（先胶囊后展开 / 直接大卡片）、「点胶囊展开卡片」开关、「点卡片打开方式」单选（小窗 / 全屏） | 三者是同一条交互链的三段（见 2.1-2），合卡后优先级一目了然；呈现改单选是因为它本来就是模式二选一（见 2.2-5） |
| 2 | 音乐卡片开关并入「打开方式」的展开逻辑旁注，仍保留独立开关但从音乐卡移出、与展开卡片相邻成组 | 同一个「点胶囊展开」概念只出现一次，音乐的特殊性用一行注脚说明，不再让用户读两张卡的说明对账（见 2.1-3） |
| 3 | 胶囊自动取色 + 胶囊滚动 + 扇子自动变淡 → 降级进外观设置卡，放在滑条区顶部做三个开关行 | 与胶囊/扇子的尺寸滑条同类同层级（见 2.3-7、2.2-6）；主页少 3 行 |
| 4 | 敏感打码四开关 → 从验证取件码卡独立成「敏感打码」卡（主页「其他」组），验证取件码卡回归只管验证码/取件码本身 | 打码已是完整功能，卡名与内容要对上（见 2.3-8）；取件码卡瘦身回原义 |
| 5 | 模拟来电 + 模拟音乐 → 移出各自卡片，合并进新卡「调试与预览」，与页脚的「功能引导」链接同组 | 纯调试工具不该混在日常功能卡里（见 2.4-10）；来电卡、音乐卡展开区大幅缩短 |
| 6 | 应用规则 / 场景例外 / 临时静默 → 不合并、只加组标题「安静规则」，并在三页说明里统一术语（见文案部分） | 三者是串联关系不是重复，合并会丢粒度；问题在术语不统一而非位置（见 2.1-4） |
| 7 | 自动消散卡保留独立行？→ 并入「打开方式」不对，它是闲置行为：与扇子自动变淡同属「没人理时怎么办」，但扇子变淡已进外观卡——自动消散 + 自动销毁（已嵌套）自成一张「自动消散」卡留在「呈现与打开」组末尾 | 点空白消散是高频行为开关，留在行为组里比塞进外观更符合直觉；与 2.1-1 的三处提及通过文案收口（只在这一张卡里讲） |
| 8 | QQ音乐免费听展示行 → 保留在音乐卡内不动 | 无开关常开功能，移走反而找不到；它的问题只是文案（见文案部分），不是位置 |
| 9 | 来电高度滑条与 callRight 解耦（建议项，需改代码逻辑而非仅 IA） | 高度对左右来电都该可调（见 2.3-9）；这是整合时顺手修的耦合，不属纯文案/布局范畴，单列出来等 wei 拍板 |

### 3.3 不动的东西

- 状态行、头部、页脚链接、检查更新、自动备份：位置和机制都合理，不动。
- 外观卡内部 11 项滑条：分组（扇子位置/胶囊/卡片/扇子图标）已经清楚，只吸收 3 个开关进来，不重排。
- 来电/音乐卡内的专属滑条：按 wei 此前「来电的在来电那一栏、音乐在音乐那一栏」的定法保留。

## 五、文案问题分析

### 5.1 风格不统一：副标题三种写法混用

- **写内容清单的**：通知气泡「左贴边胶囊 · 点开变卡片」（其实混了操作）、音乐「歌名 · 歌手 · 歌词 · 专辑图」、下载「进度条 · 速度 · 剩余时间」、来电「接听 · 挂断 · 扬声器」——名词罗列。
- **写效果的**：胶囊滚动「内容太长滚动显示」、胶囊自动取色「按 App 图标主色给胶囊上色」——动词句。
- **写操作的**：小窗打开「点卡片小窗打开 App」、展开卡片「点胶囊展开卡片（不含音乐）」——操作指令，还带括号补丁。
三种句式随机分布，扫一眼没法预判每行在讲什么。

### 5.2 重复啰嗦

- 副标题和展开说明第一句大量重复：如自动消散副标题「点空白处胶囊自动消散」vs 说明「点一下屏幕空白处，所有胶囊逐条向右消散」——展开后等于把副标题再说一遍。
- 「点屏幕空白，所有胶囊逐条向右消散」在通知气泡的说明里也出现了一次（见 2.1-1），同一行为在两张卡里各讲一遍，还不一致：一处说"向右消散"，大卡片模式里说"右滑消散成图标"。
- 打码四个子开关的副标题是同义反复：敏感打码「锁屏/录屏/投屏时验证码打码」、锁屏时打码「锁屏状态下验证码打码」、录屏/投屏时打码「录屏或投屏时验证码打码」——三行信息量约等于一行。

### 5.3 与实际行为对不上 / 表述缺口

- **展开卡片副标题「（不含音乐）」**：把实现细节（开关分工）写给用户看，用户并不关心哪个开关管音乐，只关心"点音乐胶囊会怎样"。
- **小窗打开**：名字像"能不能开小窗"，实际管的是"点卡片时小窗还是全屏打开 App"——关掉不是不开窗，是改全屏。标题与行为错位。
- **大卡片模式**：说明里才交代"音乐弹的是播放器卡片；来电还是胶囊（没有大卡片）"——模式名承诺了"大卡片"，例外藏在说明第三句。
- **自动消散**：名字像"胶囊自己会消失"，实际触发是"点空白处"，且关掉后"只能手动右滑消散或左滑收进扇子"——关键操作藏在说明末尾。
- **来电放右边**说明里才有镜像手势（往右滑钉住/往左滑挂断），副标题只说位置。

### 5.4 术语前后不一致

- 同一动作四种说法：**消散 / 销毁 / 收起 / 收纳**（自动消散、自动销毁、下载"3 秒后自动收起"、扇子收纳）——用户分不清是同一件事还是四件。
- "不弹"的三套词：**永不弹 / 只贴边 / 排队 / 突破 / 静默**（见 2.1-4）。其中「只贴边」和「贴边胶囊」里的"贴边"又和胶囊形态词重叠。
- **卡片/大卡片/展开卡片/播放器卡片/音乐卡片**：五种叫法指三种东西（普通展开卡、音乐播放卡、大卡片模式的卡），"卡片比例"在音乐卡和外观卡里各指一张卡的比例。
- **扇子**一词三义：收纳容器（扇子收纳）、整组锚点（扇子位置=整组高度）、图标堆（扇子图标）——老用户已习惯，但新文案应至少在首次出现处点明。

### 5.5 其他

- 头部副标题「通知胶囊 · 音乐 · 下载 · 取件码 · 来电」与卡名对不齐：卡叫「通知气泡」不叫「通知胶囊」，「验证取件码」缩成「取件码」。
- 反方向的钟无副标题是用户定的（不写介绍），保留，不算问题。
- QQ音乐免费听副标题「低于2小时自动补时长到4小时」是全页唯一写数字规则的副标题，与其无开关的身份不符——像个可配项，其实点不动。

## 六、重写文案（配合整合蓝图，可直接审）

**统一规矩**（先立规矩再写词）：
1. **副标题只写「管什么」**：一句、≤16 字、名词短语或"对象+行为"，不用操作指令、不用括号补丁。
2. **展开说明只写「细节和例外」**：第一句不再重复副标题；固定三段式——怎么运作 / 例外情况 / 关掉会怎样（没有就不写）。
3. **术语表全页统一**：消失动作只用「消散」（连通知一起没才用「销毁」）；收进扇子只用「收进扇子」；不弹只用「排队」（等会儿补弹）和「不弹」（永不弹）两词；卡片只分「卡片」（普通）与「播放器卡片」（音乐）。

### 6.1 胶囊类型组（5 张，标题/副标题/说明）

**通知气泡**
- 副标题：普通通知的胶囊总开关
- 说明：通知变成左贴边胶囊，点一下展开成卡片看全文。钉住的胶囊一直留着；没钉住的可以右滑消散、左滑收进扇子。永不自动展开。

**音乐胶囊**
- 副标题：音乐通知变播放器样式
- 说明：歌名、歌手、实时歌词、专辑圆盘和进度条都在胶囊和播放器卡片上。同个 App 只保留一个音乐胶囊。钉住后胶囊上显示一行加大滚动歌词。
- （卡内保留：音乐卡片开关——移出，见 6.2；音乐胶囊/卡片滑条组、恢复默认不变）

**下载与安装**
- 副标题：下载进度实时胶囊
- 说明：胶囊底部有细进度条，第二行显示已下/总量、速度和剩余时间。下载完成显示"下载完成"，3 秒后自动消散。

**验证取件码**
- 副标题：验证码复制 · 取件码钉住
- 说明：识别出验证码自动复制到剪贴板，取件码自动钉住不消散。胶囊只显示大字码、不带标题；智能柜的柜号一起显示，中英文都认。

**来电**
- 副标题：来电专属胶囊
- 说明：接听、挂断、扬声器切换都在胶囊上。来电永不自动消散。
- 子项「来电放右边」副标题：来电胶囊改放右手边；说明补一句：右边时手势镜像——往右滑钉住，往左滑挂断。

### 6.2 呈现与打开组（合并卡）

**打开方式**（新卡）
- 副标题：通知怎么出现、点开之后怎么打开
- 卡内三行：
  1. **呈现**（单选）：先出胶囊，点了再展开 / 直接出卡片
     - 说明：直接出卡片时，通知一来就是大卡片依次排列；音乐出播放器卡片，来电仍是胶囊。点空白处，卡片消散成图标收进扇子。
  2. **点胶囊展开卡片**（开关，含音乐注脚）
     - 副标题：点一下看全文，音乐胶囊同理（由下方音乐卡片开关单独控制→合并表述为：音乐的展开由「音乐卡片」行控制）

  3. **音乐卡片**（开关，从音乐卡移入）
     - 副标题：点音乐胶囊展开播放器卡片
     - 说明：关掉后点音乐胶囊直接打开音乐 App。
  4. **点卡片打开 App**（单选）：小窗 / 全屏
     - 说明：点展开的卡片打开对应 App；小窗不离开当前界面，全屏直接跳过去。

**自动消散**（保留独立卡，归入本组末尾）
- 副标题：点空白处，清掉所有胶囊
- 说明：点一下屏幕空白处，所有没钉住的胶囊逐条消散。关掉后只能右滑逐个消散、或左滑收进扇子。

## 七、设置搜索可行性

### 7.1 结论先行

**能做，难度中低，建议做。** 没有架构级障碍：设置页全部是代码动态构建的 View（LinearLayout 装进 ScrollView），所有标题/副标题/说明本来就以字符串形式存在于代码里，索引数据不用从界面上扒。主要工作量在三处：给每项补一份「关键词」数据、建一个全项注册表、做"跳转+展开+高亮"的定位协议。预计是"加一个搜索框 + 一张索引表 + 三处定位钩子"的量级，不需要重构设置页。

### 7.2 索引范围与数据来源

| 范围 | 现有数据 | 缺什么 |
|---|---|---|
| 主页 23 个 Feature（12 顶层 + 11 嵌套） | FEATURES[] 已有 key/title/subtitle/body 四个字段，现成可搜 | 关键词/同义词字段 |
| 入口卡 3 张 + 子页面 | 标题在 MainActivity 三个 build*Card 里写死；子页内行（临时静默的时长/联动/来电突破、应用规则与场景例外的档位）是各 Activity 里的局部 View | 需要在注册表里手工登记约 8–10 条（页面级 + 行级） |
| 外观设置 11 项 + 来电/音乐卡内 10 条滑条 | 标签是 buildAppearanceSliderRow 的字面量参数 | 同上，手工登记约 21 条，或给 sliderRow 加 key 参数顺手登记 |
| 页脚杂项（检查更新/重启系统界面/功能引导） | 字符串写死 | 登记 3 条即可 |

**同义词是必需品，不是锦上添花。** 只搜标题+副标题会漏掉真实说法：
- 搜「验证码」→ 应命中：验证取件码（标题含）、敏感打码（说明含"验证码"，标题不含）；
- 搜「安静」→ 应命中临时静默（全项无"安静"二字，只有静默/勿扰）；
- 搜「游戏」→ 应命中场景例外（标题不含，副标题含）；
- 搜「黑屏/挡屏幕」→ 扇子自动变淡；搜「颜色」→ 胶囊自动取色（标题是"取色"）；搜「电话」→ 来电（标题不含"电话"）。
做法：Feature 加一个 `keywords` 字段（空格分隔的同义词串），非 Feature 项在注册表里同样带 keywords。首批同义词按上表这种真实说法补，约 40 个词条以内能覆盖主要找法。

### 7.3 交互方案

- **放哪**：主页顶部常驻——头部胶囊下方、功能列表上方放一个圆角搜索框（占位文案「搜索设置，如：打码、游戏、安静」）。常驻比藏进菜单好：设置搜索的价值就在随手找。不建议做成单独搜索页，页内下拉结果更快。
- **结果呈现**：输入即出下拉列表，每条 = 标题 + 面包屑路径（如「音乐胶囊 › 音乐卡片」「外观设置 › 胶囊宽度」）。路径必须有——重名项不少（两个"卡片比例"、三个"恢复默认"），没路径分不清。
- **点结果怎么跳**：
  - 主页内的项（含嵌套子开关、卡内滑条）：滚动定位到所在卡 → 自动展开该卡 → 目标行背景闪一下（高亮 1 秒）。实现可行：卡片展开本来就是程序控制的 visibility 切换，ScrollView 用 requestRectangleOnScreen 滚到目标 View 即可；嵌套项先展开父卡再滚。
  - 子页面里的项（临时静默页的两行、应用规则/场景例外的档位）：跳进对应 Activity 并带一个 highlight 参数，子页 onCreate 后滚到该行并闪一下。三个子页都是 LinearLayout+ScrollView 的同构实现，加这个钩子是复制粘贴量级。
  - 外观卡里的滑条：外观卡本身在主页内，同主页项处理（展开外观卡 → 滚到滑条行 → 闪一下）。
- **搜不到时**：显示「没有找到，试试：打码 / 静默 / 游戏」给三个高频词作快捷入口，避免空结果死胡同。

### 7.4 与整合蓝图的关系

搜索是蓝图的**安全网**，加上之后降级更放心：
- 已计划降级进外观卡的 3 个开关（取色/滚动/扇子变淡）：降级的主要顾虑是"以后找不到"，搜索直接消掉这个顾虑。
- 移进「调试与预览」的模拟来电/模拟音乐：本来就是低频，藏深一层 + 搜「模拟/假」能命中，完全够用。
- 敏感打码的三个分开关、自动销毁这类深嵌套项：不用再为了可见性往上提层级，嵌套深度可以由逻辑决定而不是由"怕找不到"决定。
- 反过来，搜索**不能替代**整合：高频项（打开方式那条链、安静规则三件套）的结构问题是"关系不清"，不是"找不到"——搜得到也理不清。所以顺序建议：先按蓝图整合，再加搜索兜底；不要用搜索当借口跳过整合。

### 7.5 风险与注意

- 索引要跟 Feature 表同源生成（从 FEATURES[] 程序化建索引 + 一张手工登记表），避免以后加新功能忘了登记——手工表只收非 Feature 项，并写明"加新设置先登记"。
- 高亮定位依赖卡片展开动画时序：展开和滚动要串行（先展开、下一帧再滚），否则位置算错。这是唯一的实现细节坑，预览版里验一次即可。
